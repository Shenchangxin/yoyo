## 主张

现有 harness 进化论文用单元测试在公开基准上搜索，再在 **同一套题** 上报告终态分数。这有两个洞：

1. 进化本身是迭代搜索。在匹配的反馈与推理预算下，它必须和 **并行采样 / 顺序 refinement** 比，否则涨分可能只是「多试了几次」。
2. 搜索与终评共享基准，过拟合不可避免。

在 Terminal-Bench 2.1 上用 GPT-5.4 与 Claude Opus 4.6：自动 harness 进化 **并不稳定地赢过** 简单 test-time scaling；无单测反馈时平均更差。同集搜索再同集报告会夸大「harness 变好了」。

## 对 Yoyo 的含义

这是 owner 读 evolve 曲线时必须挂在嘴边的论文。Yoyo 已经有 held-out 与 transfer，比「同集自报」诚实。缺的是 **预算对照**：一轮 `evolve --k 3 --rounds 4` 烧掉的 USD，拿去跑 `eval --best N` 会怎样？

FRONTIER 议程第 1 项就是只观测、不改算法：同一张图上画 evolve 与 BoN。

不要把这篇读成「RSI 没意义」。它说的是：**评价协议** 必须把「可复用的 harness 改进」和「这道题上的额外搜索」分开。Self-Harness / ModularRSI 后续工作都在补这个洞；我们补洞的方式是不相交数据 + 记帐，不是停掉 evolve。

## 可偷 / 应拒

- 偷：匹配预算协议；held-out 泛化才算数；BoN / sequential refinement 作为 evolve 的对照基线。
- 拒：因为这篇就删掉 Harbor 门 — 门仍然挡住安全失败和回退。
- 产品措辞：不要对用户说「evolve 一定比多采样更强」，说「evolve 产生可回滚的 harness 状态；是否值得花这次预算，看实验室对照」。
