## 主张

把 RSI 用在 harness 上之后，泛化仍被三件事卡住：

1. 在评测基准（或其子集）上进化，分不清「可复用改进」和「背下这套题」。
2. 单条轨迹把 **系统性 harness 缺陷** 和 **这道题的推理细节** 缠在一起。
3. 整包优化让无关机制互相污染，无法归因。

ModularRSI 的回答：

- **对比**：同一任务的成功轨迹 vs 失败轨迹，再跨任务聚合，只保留反复出现的行为缺陷。
- **模块**：可进化 harness 拆成五个功能块 — Agent Loop、Tool Use、Observation Management、Context Management、Task Completion Detection。每块在受限范围内独立进化，再进入集成阶段解冲突。
- **数据不相交**：从外部来源整理 2000 道可执行进化任务，与 TB2.0 / SWE-Verified **完全分开**。进化后冻结 harness，再评测。

报告：TB2.0 47.57 → 52.43，SWE-Verified 73.40 → 76.45；跨域与跨模型仍有增益。评测在 Harbor 框架下进行。

## 对 Yoyo 的含义

Yoyo 的 L1 表面（playbook / fragment / skill / instruction / middleware）已经是「有界补丁」，但 **不是** 这五个运行时模块，也没有「一次只动一块再 merge」。evolve 的证据主要来自同一套 suite 的 held-in。这是 FRONTIER 议程 2–5 的直接来源。

不要把五模块理解成再引入一套 agent 框架。它是 **提案作用域** 的纪律：例如只改「何时宣布任务完成」，不动工具描述。

## 可偷 / 应拒

- 偷：同任务对比；进化集 ⊥ 评测集；模块受限补丁 + 集成。
- 拒：为了模块化而允许 evolve 改 Go 里的 loop 拓扑（那是 L3/L4）。
- 最小实验：repeats≥2 时把 pass/fail 轨迹成对放进 `EvidenceBundle`；sealed held-in 再切一刀专供 evolve。
